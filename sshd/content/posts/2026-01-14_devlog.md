# Importance of skeleton loading for customer trust

Skeleton loading is a given in many modern applications. This is where you have some animated shape as a placeholder for content/resources while it's being fetched. Mainly we think we do this because it looks nicer and it allows there to start being some meaningful UI state before everything is loaded which makes the load times feel faster.

Today, we hit an issue where we had a section of the app that loaded pretty fast but there wasn't a skeleton loading state. When we tested it we thought it felt fine and we could move on, but from the user's perspective what they saw was initially a blank section and then less than a second later the content showed up. You wouldn't think that milliseconds would make that much of a difference but the feedback we got was they thought all of their work had been deleted or dissapeared for those brief moments which made them feel like the product was untrustworthy and could not be used to do business critical tasks.

We won't make that mistake again and will be taking an audit of other flows within the app where we need to missing skeleton loaders.

# Still working on replacing Retool

When the company started GPT-2.5 was still a few months away and we were still in the mindset of we needed to purchase all of these tools that offloaded a lot of work so we could move faster and focus on our product. Those tools have a high premium for offloading that work.

One of the tools we use is Retool. I honestly think its a good product and I have this whole spiel about how operational tools like this should and will replace traditional BI products, but considering our product is a pseudo-BO product there is too much overlap and we need to dogfood more.

For Retool reports where we give it a user/team and have it fetch all of these records and aggregations we care about we now just do that in our own product. For admin tasks like deleting a user/team we have moved almost all of that to a CLI tool.

At this point we are probably 90% there so we should be able to get rid of Retool over the next week or so.

Since the CLI tool is not customer facing, we have been letting Claude Code do some of that work to reduce non-critical workload for team members (more thoughts on this below).

# Claude Code musings

I've been pretty bummed about the state of the industry over the last 11 months[^1]. A lot of it has to do with my feeling that these tools make lazier, less capable engineers but I'm also human and sometimes I want to do things the easier way instead of the hard way.

I'm trying to be thoughtful about when to use these tools and a few things that have worked for me in the sense that I don't totally hate it is the following:

- [x] Enable Claude Code GitHub PR review
- [x] Set output mode in Claude Code to `learning` so it doesn't try to do your work for you
- [x] Embrace it as a better search that can be context aware
- [x] Put a lot of effort in on CI (static analysis, linting, dead code analysis, unit tests, integration tests, e2e/API tests, etc.)

I'm on a team where the majority are using Claude Code, Cursor, or something else and even though I still feel like my output and quality level is better than most I can't force people to share my opinions or use my tools. What I can do it make sure that guardrails are in place and to know how to help my teammates use these tools to increase the output and quality.
