# Stripe billing: price tiers and accumulating meter events

We're setting up a hybrid flat rate + usage-based billing for the product. User's pay a flat one time price per month that comes with a certain amount of compute hours and tokens but then we chart a per-unit price on any volume above the allocated amounts.

Like most startups and modern software companies, we use Stripe for billing. I've had to learn a lot about Stripe in order to do build this for us.

One feature that unlocks this for us is [tiered pricing](https://stripe.com/ie/resources/more/tiered-pricing-101-a-guide-for-a-strategic-approach). This allows us to do exactly what we want to do, chart $0 for units [1-N] and $X dollars for units [N+1-, inf).

For all units, we will send meter events to capture units and then sum those up at the end of the month for billing accounts.

There are a few tricky parts about this for us:

1. For token usage, we will charge $X/mTokens (million tokens). Since Stripe doesn't allow floating point values for units and we are mainly using serverless compute instances, we cannot easily accumulate and flush values in the system. Stripe also does not support <$0.01 values for prices so we cannot price at $Y/token. To split the difference I've decided to use kToken (one thousand tokens) as the unit. This seems reasonable since the majority of agent sessions use >= 1 kTokens so I'm not too worried about flooring to zero.
2. For compute hour we charge $X/hour, but the majority of our billable compute events last <= 10s and some last <= 1s. This brings us back to the issue of not being able to accumulate in the server and Stripe not allowing floating point units in meter events. For this I couldn't really find a more obvious middle ground between the units that we show on our pricing page and the actual billing units in Stripe (e.g. mToken -> kToken). Another thing is we do not want to overwhelm the Stripe API by making the unit 1s of compute and sending potentially hundreds or thousands of events per second.

To alleviate some of these issues, what I've decided to do is to write meter events to an intermediate accumulator store and then flush those at some lower frequency (likely every hour or so).

That way we can accurately record small units like 1 token and 1ms of compute, aggregate those values over some timespan, and then send it all at once.

Right now, this is just in the brainstorming phase but so far I'm liking it.

# Playing around with `fanotify` and `inotify`

Something I've had on my mind for awhile is file watching utilities (i.e. `watchman`, `watchexec`, `enter`, and my own [`ssfw`](https://github.com/mharrisb1/ssfw)). I wrote mine when I was very new to systems programming and had no idea what I was doing beyond being able to copy some examples from a popular Rust crate.

Even with my shitty first pass, I've used the utility almost everyday since. I've also become highly sensitive to problems where having a good file watcher is needed.

Like all engineers I like to abstract and then abstract more. As I get more comfortable and knowledgable about systems programming, I'm able to see file watchers as just a specific use case of event systems.

Overtime I've been playing with this idea in my head of a utility or suite that can be a drop in replacement for any file watcher but allows the user to expand beyond just file system events. The pitch in my head is a suite for full system observability (whatever that entails).

The idea is still too fuzzy to act on but I like to experiment every now and then with APIs that could possibly be used in such a suite.

Today, I saw a random post about `fanotify` which is newer and separate from `inotify`. It's billed as being a modern replacement for certain use cases so I wanted to play around with it and see if maybe I could write a new file watcher to support that as the backend since I couldn't find many others that did.

I ran into some pretty big issues that killed that thought. The need to run as root is definitely a blocker and then the absolute onslaught of events since you need to subscribe to the whole filesystem and the need to add filtering middleware was just too much.

I definitely see the use cases for SecOps, networked filesystems, and other things like that where you _do_ want to see every file system event across the system, but for what I was looking for, it was just too much.

# Implementing a HashSet in C

I've been studying up on data structures and algorithms as part of [CS Primer](https://csprimer.com) and as part of interview prep. One of the questions I worked on today was a Leetcode easy about identifying if an array contains duplicates with the goal of finding a solution with $O(n)$ time and space complexity. This was indeed easy and I knew to use a [`unordered_set`](https://en.cppreference.com/w/cpp/container/unordered_set.html) (using C++):

```cpp
class Solution {
public:
    bool hasDuplicate(vector<int>& nums) {
        unordered_set<int> counter;
        for (int n : nums) {
            if (counter.contains(n)) {
                return true;
            }
            counter.insert(n);
        }
        return false;
    }
};
```

But, I'm always tripping down new rabbit holes so I wanted to take a stab at actually implementing a HashSet in C. I've never looked up an implementation for that but I have written toy HashMaps in C so it was easy to translate from a KV mapping to a set but still using buckets and chaining. For the API I tried to implement as much of C++ `unordered_set` as I could until it became tedious.

```c
// llist.h
#ifndef LLIST_H
#define LLIST_H
typedef struct llist_t {
    struct llist_t *next;
    int             val;
} llist_t;

// allocation
llist_t* llist_new();
void     llist_free(llist_t *node);

// modifiers
void llist_insert_at(llist_t *node, size_t index, int val);
void llist_delete_at(llist_t *node, size_t index);

// lookup
int llist_find(llist_t *node, int value);
#endif // LLIST_H
```

```c
// hashset.h
#ifndef HASHSET_H
#define HASHSET_H
#include "llist.h"

typedef struct {
    size_t    buckets;
    llist_t **chains;
} hashset_t;

// allocation
hashset_t* hashset_new();
void       hashset_free(hashset_t *set);

// capacity
int    hashset_is_empty(hashset_t *set);
size_t hashset_size(hashset_t *set);

// modifiers
void hashset_clear(hashset_t *set);
void hashset_insert(hashset_t *set, int value);
void hashset_delete(hashset_t *set, int value);

// lookup
void hashset_contains(hashset_t *set, int value);

#endif // HASHSET_H
```

```c
// main.c
#include <stdbool.h>

#include "hashset.h"

int main() {
    hashset_t *set = hashset_new();

    // insert values (including dupes);
    hashset_insert(set, 1);
    hashset_insert(set, 2);
    hashset_insert(set, 2);
    hashset_insert(set, 3);
    hashset_insert(set, 4);
    hashset_insert(set, 4);

    // ensure dupes weren't inserted
    assert(hashset_size(set) == 4);

    // ensure we can find values
    assert(hashset_contains(set, 1) == true);
    assert(hashset_contains(set, 2) == true);
    assert(hashset_contains(set, 3) == true);
    assert(hashset_contains(set, 4) == true);
    assert(hashset_contains(set, 5) == false);

    // ensure we can clear values
    assert(hashset_empty(set) == false);

    hashset_clear(set);
    assert(hashset_empty(set) == true);

    // ensure we can delete values
    hashset_insert(set, 1);
    hashset_insert(set, 2);
    hashset_insert(set, 3);
    hashset_insert(set, 4);
    assert(hashset_empty(set) == false);

    hashset_delete(set, 1);
    hashset_delete(set, 2);
    hashset_delete(set, 3);
    hashset_delete(set, 4);
    assert(hashset_empty(set) == true);

    // free hashset and chains
    hashset_free(set);
}
```

Overall was a fun exercise. I tripped up a little on insert, delete, and contains only because my initial approach actually allocated the head nodes for all the chains instead of allowing those to be `NULL`. This tripped be up because I had to sprinkle `if (node->val == NULL)` in abunch of places which just made it harder to reason about.

I also benefited from a refactor where I pushed as much down to the linked list as possible to utilize common algorithms there like search, delete, insert, etc. instead of having that logic in the hashset algorithms.

Next, I want to attempt a template-like HashSet in C where it can accept arbitrary types but I need to think harder about what a good DX would look like since you would need to allow the user to provide their own functions for hashing, equality, etc. as well as providing default ones for common types like `int`, `float`, `char*`, etc.

I also need to explore hashing functions for C since I really have never written a robust one that doesn't suffer from frequent(-ish) collisions.
