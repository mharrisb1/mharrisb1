# Replacing Playwright PDF exports with modern-screenshot

One of my teammates added [`modern-screenshot`](https://github.com/qq15725/modern-screenshot) in order to given the agent a screenshot of the current dashboard as context. They stumbled upon it by reading [Monday.com's engineering blog post about why they chose to use it for exports](https://engineering.monday.com/capturing-dom-as-image-is-harder-than-you-think-how-we-solved-it-at-monday-com).

One thing I liked about it was that you could precisely target the part of the DOM that you want to export. This popped out at me because for awhile, I've had a ticket on my backlog to fix the automated dashboard exports to email and Slack to fix some of the jankiness encountered from using Playwright. The two big issues were:

1. Multiple-page PDFs because Playwright would capture, scroll, and capture again until it exhausted the scroll height.
2. Need to adding one-off URL params to hide content like the sidebars or the agent prompt input

By allowing me to target exactly what to export, and to do it in a way that did not break up the dashboard into separate pages in a PDF allowed me to enhance the user's experience vastly.

The only difficult part was instrumenting the application in a way to allow some export controllers as part of the global window object for Playwright to control.

# A (potentially) better file watcher

I've mentioned before that something I'm interested in is file watcher utilities.

Some popular ones are:

- [Watchman](https://facebook.github.io/watchman)
- [watchexec](https://github.com/watchexec/watchexec)
- [entr](https://github.com/eradman/entr)

I've also written an admittedly terrible one:

- [ssfw](https://github.com/mharrisb1/ssfw)

I've thought about writing a better one time and time again, but I've just never been satisfied by the limited scope of watch some directory using something like `inotify` and then running some command when an event is detected. Something just always felt missing.

Recently, I ran into a problem that kind of involved the same premise: watch for some state change and then trigger something. This abstraction actually got me excited. Instead of building _just_ a file watcher utility, I want to build a general purposed state change observation system. I don't have a clear picture yet, but I think having file watchin as an implementation of a broader system is an interesting idea. Some things that you could do with this sytem:

- Hot reloading a server
- Continuous testing
- Linting + formatting pipelines
- Code generation
- Build pipelines
- Deployment automation
- Artifact pipelines
- Config change propagation
- Distributed dev environments
- Data ingestion pipelines
- API change detection
- Event-driven workflows
- Config drift detection
- Secrets rotation
- Policy enforcement
- Kubernetes automation
- Infrastructure monitoring
- Log-driven automation
- Performance regression detection
- IDE file watching engine
- Editor plugins
- Golden file regeneration
- Fuzzing automation
- Integration test orchestration
- ML training pipelines
- Universal trigger engine
- Event debugging / replay
