# FinOps(-ish)

I've recently fallen into a role that I like to think of as a union of Software Engineering and Accounting. When I ask ChatGPT what that type of role is, it usually ends up saying "FinOps".

To date I've been able to help the team save 40% plus on Cloud billing. On its face, that does sound like FinOps and there were tons of low hanging fruit like tightening inter zone egress, killing old and unused services, etc. But there has also been some more interesting work that I feel falls outside of what I consider "FinOps" roles like:

- Rearchitecting to support multi-tenancy to better utilize resources
- Rewriting off-the-shelf libraries and frameworks to be better tuned for your infrastructure
- Moving all client-side resource fetching to JIT to avoid as much network and database access as possible
- Instrumenting the system for reliable usage-based billing

A lot of these are pretty standard software engineering/performance engineering tasks so maybe this is still within my normal role but I've very much enjoyed optimizing for costs and/or profit and being able to frame the problem in that way instead of the normal individual user-centric framing.

With a Dad thats an engineer and a Mom that is an accountant I think maybe my brain is wired for this sort of role or at least problem framing so I'm going to keep a bead on whatever this is. In my immagination I see there being an exclusive role that requires you to go deep on both the technical and business domains to work on these types of problems and I've either just not found out what that role is yet or it's something I'd like to create.

# Cloud Run blows up

We've had a weird bug the last few weeks where we deploy to production and everything just blows up. Site is unusable and users are frustrated. What's been even more of a headache is our normal ways of diagnosing a proble weren't available. Nothing was being sent to Sentry, logs were sparse, no resource metrics, nothing.

After a few minutes the problem would go away and we wold just move on until the next deployment where it would happen again.

Thankfully, one of our engineers found the cause today and we were able to fix it.

tl;dr is we are using Cloud Run for a lot of our business logic services and Cloud Run has a nasty quirk that must have recently been introduced where there is a race condition between the service starting and NAT path being registered.

So for the first few minutes of an instance coming up, it is unable to connect to any networked service.

And unfortunately, almost all of our observability stack is push based so since the service can't push out traces, logs, and metrics we had heard nothing while the product was bricked.

To make it more complicated, the deployment strategy we have is full replacement of instances so as soon as we deploy it breaks for everyone instead of doing a gradual release where the bricked instances would be reported as unhealthy and would stop being served behind the gateway.

We found Google's suggested workaround about configuring a startup probe and that resolved the issue.

https://docs.cloud.google.com/run/docs/configuring/vpc-direct-vpc
