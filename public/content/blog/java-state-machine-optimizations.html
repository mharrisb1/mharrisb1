Initial implementation

It's cliche to pick Gang of Four Design Patterns, but unlike others who do it I:

  1. Understand that I know very little and am not smart than them
  2. Understand that what those patterns optimize for is maintaining large scale, industrial codebases

Still, here goes another sloppy blog post that's going to use one of these patterns as a counterexample to performant, data-oriented programming. So with my best Casey Muratori impression, here is this dog shit first implementation of our state machine. 


public enum Input { CLICK_A, CLICK_B, CLICK_N }             // our 3 input options
public enum State { NULLSET, INTERSECT, SET_A, SET_B, ... } // our 8 states
public class Fsm {

    IStateNode clickN();
    IStateNode clickA();
    IStateNode clickB();
    State getState();
  }

  public static class NullSetState implements IStateNode {
    @Override public IStateNode clickN() { return new IntersectState(); }
    @Override public IStateNode clickA() { return new SetAState(); }
    @Override public IStateNode clickB() { return new SetBState(); }
    @Override public State getState() { return State.NULLSET; }
  }

  public static class IntersectState implements IStateNode {
    @Override public IStateNode clickN() { return new NullSetState(); }
    @Override public IStateNode clickA() { ... }
    @Override public IStateNode clickB() { ... }
    @Override public State getState() { ... }
  }

  public static class SetAState implements IStateNode { ... }
  public static class SetBState implements IStateNode { ... }
  public static class ADiffBState implements IStateNode { ... }
  public static class BDiffAState implements IStateNode { ... }
  public static class UnionState implements IStateNode { ... }
  public static class SymDiffState implements IStateNode { ... }

  private IStateNode currentState;
  public Fsm() { this.currentState = new NullSetState(); }

  public voif transition(Trigger trigger) {
    switch (trigger) {
      case CLICK_A: currentState = currentState.clickA(); break;

Admittedly, this isn't even bad looking code, and if you just needed a state machine that has no non-functional requirements around performance, then this is fine. You could get hit by a bus tomorrow and the poor junior engineer that has to deal with your garbage code can look at this and know what's going on.

If you do need a high-performance state machine then this design pattern should immediately be ruled out. Let's look at some data.

Our contrived benchmark

I set up a benchmark to test our state machine designs against a purely ficticious scenario of needing to handle 10 million inputs as fast as possible.

No, there is no reason why this state machine would need to do that. When I port it to JavaScript it will just need to handle user clicks. Even if you're spamming your mouse you're not going to get to 10 million input events.

However, this example state machine serves as a good proxy for a machine you might have to write for processing network traffic, deterministically handling user inputs and state transitions in an online game, etc. We'll get to another one this state machines good properties that will allow us to tune it more than we could with other potential state machines.

Using OpenJDK's Java Microbenchmark Harness (JMH) we can write a simple benchmark like this: 


import org.openjdk.jmh.annotations.*;

import java.util.Random;
import java.util.concurrent.TimeUnit;

@State(Scope.Benchmark)
@BenchmarkMode(Mode.Throughput)
@OutputTimeUnit(TimeUnit.SECONDS)
@Warmup(iterations = 3, time = 2)
@Measurement(iterations = 5, time = 20)
@Fork(1)
public class Benchmark {
  private static final int ITERATIONS = 10_000_000;
  private Input[] inputs;
  private Fsm fsm;

  @Setup(Level.Trial)
  public void setup() {
    inputs = Input[ITERATIONS];
    fsm = new Fsm();

    Random rand = new Random(42);
    Input[] values = Input.values();

    for (int i = 0; i < ITERATIONS; i++) {
      inputs[i] = values[rand.nextInt(values.length)];
    }
  }

  @Benchmark
  @OperationsPerInvocation(ITERATIONS)
  public State measure() {
    for (int i = 0; i < ITERATIONS; i++) {
      fsm.transition(inputs[i]);
    }
    return fsm.getState(); // return this so JVM doesn't optimize all the work above away
  }
}

Our starting point: the initial benchmark results

JMH provides many useful stats, but we're going to focus on four main ones:

Metric Description
Throughput The total number of state transitions the machine can process per second. Higher is better.
Allocations The number of bytes allocated on the heap per operation. High allocations lead to Garbage Collection pauses and degraded performance.
Branch Misses The number of CPU branch mispredictions per operation. Mispredicts cause the CPU pipeline to flush, wasting valuable clock cycles.
L1 D-Cache Misses The number of times the CPU failed to find the required data in the L1 Data Cache per operation, forcing it to fetch from slower memory.

Here are the numbers from our initial implementation using a canonical state pattern design:

  • Throughput: 73,440,877 ops/s
  • Allocations: 16.000 B/op
  • Branch Misses: 1.212 /op
  • L1 D-Cache Misses: 0.337 /op

Tuning Part 1: Focus on allocations

The main thing we should keep in mind as we tune our state machine is that the north star is increasing the ops/s metric. However, that is a lagging metric. We can really only improve that number by improving the others. So, first up let's focus on those 16 bytes being allocated per operation.

We should all know that Java will generally allocate objects on the heap which has a much higher cost than allocating to the stack. This is why 16 B/op is such a drag on our throughput. Not only that, but we have to also track and garbage collect that memory resulting in frequent, expensive stops to the program. Anyone who has ever viewed those nasty periodic spikes in a Grafana dashboard knows how problematic this can be.

We can also perfectly reason about what those 16 bytes are:

Component Size (Bytes) Description
Object Header 12 Standard JVM object header.
Object Payload 0 Our state classes (e.g. SetAState) contain no fields or instance variables.
Padding 4 The JVM pads objects to 8-byte boundaries.

In general, the less allocations we do the better, especially in a hot loop. This will be the first thing we focus on for refactoring.

To avoid allocating a new object for every transition we'll move away from the state pattern design and use something more prosaic: a simple switch-case design. 


public enum Input { CLICK_A, CLICK_B, CLICK_N }             // our 3 input options
public enum State { NULLSET, INTERSECT, SET_A, SET_B, ... } // our 8 states
public class Fsm {
  private State currentState;
  public Fsm() { this.currentState = State.NULLSET; }

  public void transition(Input input) {
    switch (currentState) {
      case NULLSET:
        switch (input) {
          case CLICK_A: currentState = State.SET_A; break;
          case CLICK_B: currentState = State.SET_B; break;
          case CLICK_N: currentState = State.INTERSECT; break;
        }
        break;
      case INTERSECT:
        switch (input) {
          case CLICK_A: ...; break;
          case CLICK_B: ...; break;
          case CLICK_N: ...; break;
        }
        break;
      case SET_A: ...; break;
      case SET_B: ...; break;
      ...
    }
  }
}

This implementation will avoid allocations entirely other than the main Fsm class initialization which isn't even included in the benchmark.

We should explicitly call out that creating all of those nested switch-case statements is cumbersome and error prone. That is exactly why for larger projects, the Gang of Four pattern is generally worth the performance hit. Still, let's keep going and see the results:

Metric GoF (Initial) Switch-Case Delta
Throughput 73,440,877 ops/s 134,087,417 ops/s +82.6%
Allocations 16.000 B/op ~ 0 B/op -100%
Branch Misses 1.212 /op 0.717 /op -40.8%
L1 D-Cache Misses 0.337 /op 0.067 /op -80.1%

Look at that, we've already almost doubled our throughput and we can see that we've completely eliminated the bytes allocted per operation. This is a huge leap in performance and we could easily stay here and call it a day, but what fun would that be?

Tuning Part 2: What about those branch misses?

Before I go any deeper, modern hardware is incredibly complex and our mental models of how they actually work is probably not as great as we think. I say that because I do not know exactly how the complex execution pipelines work. If I did, I would have been able to write exploits like these. Treat this as a blanked CYA for what I'm about to say next.

Modern CPUs try to run as fast as physically possible. As we hit physical limits we start to introduce neat tricks to extract even more performance. One of those tricks is that a CPU will start working on the next instruction (or several) before the previous one is finished. This can be super helpful, but sometimes it can actually be hurtful to performance.

When the CPU reaches an instruction that causes a branch (if, switch, etc.), then the CPU needs to guess, or to give it a facade of authority, predict, which way to go for the branch. Thanks to the mathematical prowess of some truly impressive engineers and scientists, we're can predict reasonably well, but sometime we get it wrong and that is called a "branch miss". This results in the CPU having to back track and go back down the correct branch before continuing.

Taking a look at the new state machine implementation we have, you can probably guess that all those nested switch statements give the CPU a hard time. What we want to do it use a design that eliminates branching entirely.

For our next refactor, we'll use a state table. For our state machine, we can represent it as a 2D table:

Current State \ Input CLICK_N CLICK_A CLICK_B
NULLSET INTERSECT SET_A SET_B
INTERSECT NULLSET SET_A SET_B
SET_A A_DIFF_B NULLSET UNION
SET_B B_DIFF_A UNION NULLSET
A_DIFF_B SET_A NULLSET SYMDIFF
B_DIFF_A SET_B SYMDIFF NULLSET
UNION SYMDIFF SET_B SET_A
SYMDIFF UNION B_DIFF_A A_DIFF_B

Translated to code, our state machine will now look like this:


public final class FsmConstants {
  // Triggers
  public static final int CLICK_N = 0;
  public static final int CLICK_A = 1;
  public static final int CLICK_B = 2;

  // States
  public static final int NULLSET = 0;
  public static final int INTERSECT = 1;
  public static final int SET_A = 2;
  public static final int SET_B = 3;
  public static final int A_DIFF_B = 4;
  public static final int B_DIFF_A = 5;
  public static final int UNION = 6;
  public static final int SYMDIFF = 7;

  private FsmConstants() {
  } // Prevent instantiation
}

public class Fsm {

  private static final int[][] STATE_TABLE = {
      // [CLICK_N] [CLICK_A] [CLICK_B]
      /* NULLSET */ { INTERSECT, SET_A, SET_B },
      /* INTERSECT */ { NULLSET, SET_A, SET_B },
      /* SET_A */ { A_DIFF_B, NULLSET, UNION },
      /* SET_B */ { B_DIFF_A, UNION, NULLSET },
      /* A_DIFF_B */ { SET_A, NULLSET, SYMDIFF },
      /* B_DIFF_A */ { SET_B, SYMDIFF, NULLSET },
      /* UNION */ { SYMDIFF, SET_B, SET_A },
      /* SYMDIFF */ { UNION, B_DIFF_A, A_DIFF_B }
  };

  private int currentState;

  public Fsm() {
    this.currentState = NULLSET;
  }

  public void transition(int input) {
    currentState = STATE_TABLE[currentState][input];
  }

  public State getState() {
    return State.values()[currentState];
  }
}

This code is quite simple and compact to the point where I included the entire snippet above. A few small notes to make are:

  1. We dropped the enums and went write to constant static integers. This avoids the call to enum's ordinal() method.
  2. I still kept the getState() return type the same since it's not in the benchmark's hot path.
  3. The input list in benchmark is now comprised of integers instead of enum values.
