State Machine Tuning: 850% Performance Improvement

2026-07-20

What we're building

The state machine we're going to be using as an example is one that I actually need for a future blog post going over optimizing sets in Python. For that post, I want to display an interactive graphic of a Venn diagram where the user can click either set A , B, or A ∩ B . We treat those as the valid inputs to the machine. Starting with the initial state of ∅, given just those 3 inputs we can span a total of 8 possible states.

Description Mathematical Repr Enum Name
Null Set ∅ NULLSET
Intersection A∩B INTERSECT
Set A A SET_A
Set B B SET_B
A Difference B A∖B A_DIFF_B
B Difference A B∖A B_DIFF_A
Union A∪B UNION
Symmetric Difference AΔB SYMDIFF

Initial implementation

It's cliche to pick on Gang of Four Design Patterns, but unlike others who do it I:

  1. Understand that I know very little and am not smarter than them
  2. Understand that what those patterns optimize for is maintaining large scale, industrial codebases

Still, I'm going to start with a design that you've probably used in your codebase or have at least seen a few times. 


public enum Input { CLICK_A, CLICK_B, CLICK_N }             // our 3 input options
public enum State { NULLSET, INTERSECT, SET_A, SET_B, ... } // our 8 states
public class Fsm {
  public interface IStateNode {
    IStateNode clickN();
    IStateNode clickA();
    IStateNode clickB();
    State getState();
  }

  public static class NullSetState implements IStateNode {
    @Override public IStateNode clickN() { return new IntersectState(); }
    @Override public IStateNode clickA() { return new SetAState(); }
    @Override public IStateNode clickB() { return new SetBState(); }
    @Override public State getState() { return State.NULLSET; }
  }

  public static class IntersectState implements IStateNode {
    @Override public IStateNode clickN() { return new NullSetState(); }
    @Override public IStateNode clickA() { ... }
    @Override public IStateNode clickB() { ... }
    @Override public State getState() { ... }
  }

  public static class SetAState implements IStateNode { ... }
  public static class SetBState implements IStateNode { ... }
  public static class ADiffBState implements IStateNode { ... }
  public static class BDiffAState implements IStateNode { ... }
  public static class UnionState implements IStateNode { ... }
  public static class SymDiffState implements IStateNode { ... }

  private IStateNode currentState;
  public Fsm() { this.currentState = new NullSetState(); }

  public voif transition(Trigger trigger) {
    switch (trigger) {
      case CLICK_A: currentState = currentState.clickA(); break;
      case CLICK_B: currentState = currentState.clickB(); break;
      case CLICK_N: currentState = currentState.clickN(); break;
    }
  }

  public State getState() { return this.currentState.getState(); }
}

Admittedly, this isn't even bad looking code, and if you just needed a state machine that has no requirements around performance, then this is fine. You could get hit by a bus tomorrow and the poor junior engineer that has to deal with your code can look at this and know what's going on.

If you do need a high-performance state machine then this design pattern should immediately be ruled out. Let's look at some data.

Our starting point: the initial benchmark results

I set up a benchmark to test our state machine designs against a purely ficticious scenario of needing to handle 10 million inputs as fast as possible.

No, there is no reason why this state machine would need to do that. When I port it to JavaScript it will just need to handle user clicks. Even if you're spamming your mouse you're not going to get to 10 million input events.

However, this example state machine serves as a good proxy for a machine you might have to write for other domains.

Using OpenJDK's Java Microbenchmark Harness (JMH) we can write a simple benchmark like this: 


import org.openjdk.jmh.annotations.*;

import java.util.Random;
import java.util.concurrent.TimeUnit;

@State(Scope.Benchmark)
@BenchmarkMode(Mode.Throughput)
@OutputTimeUnit(TimeUnit.SECONDS)
@Warmup(iterations = 3, time = 2)
@Measurement(iterations = 5, time = 20)
@Fork(1)
public class Benchmark {
  private static final int ITERATIONS = 10_000_000;
  private Input[] inputs;
  private Fsm fsm;

  @Setup(Level.Trial)
  public void setup() {
    inputs = Input[ITERATIONS];
    fsm = new Fsm();

    Random rand = new Random(42);
    Input[] values = Input.values();

    for (int i = 0; i < ITERATIONS; i++) {
      inputs[i] = values[rand.nextInt(values.length)];
    }
  }

  @Benchmark
  @OperationsPerInvocation(ITERATIONS)
  public State measure() {
    for (int i = 0; i < ITERATIONS; i++) {
      fsm.transition(inputs[i]);
    }
    return fsm.getState(); // return this so JVM doesn't optimize all the work above away
  }
}

JMH provides many useful stats, but we're going to focus on four main ones:

Metric Description
Throughput The total number of state transitions the machine can process per second. Higher is better.
Allocations The number of bytes allocated on the heap per operation. High allocations lead to Garbage Collection pauses and degraded performance.
Branch Misses The number of CPU branch mispredictions per operation. Mispredicts cause the CPU pipeline to flush, wasting valuable clock cycles.
L1 D-Cache Misses The number of times the CPU failed to find the required data in the L1 Data Cache per operation, forcing it to fetch from slower memory.

Here are the numbers from our initial implementation using a canonical state pattern design:

  • Throughput: 73,440,877 ops/s
  • Allocations: 16.000 B/op
  • Branch Misses: 1.212 /op
  • L1 D-Cache Misses: 0.337 /op

Tuning Part 1: Focus on allocations

The main thing we're trying to achieve here is higher throughput. However, that is a lagging metric. We can really only improve that number by improving the others. So, first up let's focus on those 16 bytes being allocated per operation. Since this is Java, they are also being allocated on the heap instead of the stack. Not only that, but we have to also track and garbage collect that memory.

Here's what those 16 bytes are:

Component Size (Bytes) Description
Object Header 12 Standard JVM object header.
Object Payload 0 Our state classes (e.g. SetAState) contain no fields or instance variables.
Padding 4 The JVM pads objects to 8-byte boundaries.

So all of those allocations aren't even really useful since they are entirely metadata. Avoiding these allocations will be our first area of focus.

To avoid allocating a new object for every transition we'll move away from the state pattern design and use something more prosaic: a simple switch-case design. 


public enum Input { CLICK_A, CLICK_B, CLICK_N }             // our 3 input options
public enum State { NULLSET, INTERSECT, SET_A, SET_B, ... } // our 8 states
public class Fsm {
  private State currentState;
  public Fsm() { this.currentState = State.NULLSET; }

  public void transition(Input input) {
    switch (currentState) {
      case NULLSET:
        switch (input) {
          case CLICK_A: currentState = State.SET_A; break;
          case CLICK_B: currentState = State.SET_B; break;
          case CLICK_N: currentState = State.INTERSECT; break;
        }
        break;
      case INTERSECT:
        switch (input) {
          case CLICK_A: ...; break;
          case CLICK_B: ...; break;
          case CLICK_N: ...; break;
        }
        break;
      case SET_A: ...; break;
      case SET_B: ...; break;
      ...
    }
  }
}

Let's see the results:

Metric GoF (Initial) Switch-Case Delta
Throughput 73,440,877 ops/s 134,087,417 ops/s +82.6%
Allocations 16.000 B/op ~ 0 B/op -100%
Branch Misses 1.212 /op 0.717 /op -40.8%
L1 D-Cache Misses 0.337 /op 0.067 /op -80.1%

Look at that, we've already almost doubled our throughput and we can see that we've completely eliminated the bytes allocted per operation.

Tuning Part 2: What about those branch misses?

Modern CPUs try to run as fast as physically possible. As we hit physical limits we start to introduce neat tricks to extract even more performance. One of those tricks is that a CPU will start working on the next instruction (or several instructions!) before the previous one is finished. This can be super helpful, but sometimes it can actually be harmful to performance.

When the CPU reaches an instruction that causes a branch (if, switch, etc.), then the CPU needs to predict which way to go. CPUs can predict reasonably well, but sometime it will be wrong and have to back track. This is called a "branch miss".

Taking a look at this implementation, you can probably guess that all those nested switch statements give the CPU a hard time. What we want to do it use a design that eliminates branching entirely.

For our next refactor, we'll use a state table. We can represent our state machine as a 2D table:

Current State \ Input CLICK_N CLICK_A CLICK_B
NULLSET INTERSECT SET_A SET_B
INTERSECT NULLSET SET_A SET_B
SET_A A_DIFF_B NULLSET UNION
SET_B B_DIFF_A UNION NULLSET
A_DIFF_B SET_A NULLSET SYMDIFF
B_DIFF_A SET_B SYMDIFF NULLSET
UNION SYMDIFF SET_B SET_A
SYMDIFF UNION B_DIFF_A A_DIFF_B

Translated to code, our state machine will now look like this:


public final class FsmConstants {
  // Triggers
  public static final int CLICK_N = 0;
  public static final int CLICK_A = 1;
  public static final int CLICK_B = 2;

  // States
  public static final int NULLSET = 0;
  public static final int INTERSECT = 1;
  public static final int SET_A = 2;
  public static final int SET_B = 3;
  public static final int A_DIFF_B = 4;
  public static final int B_DIFF_A = 5;
  public static final int UNION = 6;
  public static final int SYMDIFF = 7;

  private FsmConstants() {
  }
}

public class Fsm {

  private static final int[][] STATE_TABLE = {
      // [CLICK_N] [CLICK_A] [CLICK_B]
      /* NULLSET */ { INTERSECT, SET_A, SET_B },
      /* INTERSECT */ { NULLSET, SET_A, SET_B },
      /* SET_A */ { A_DIFF_B, NULLSET, UNION },
      /* SET_B */ { B_DIFF_A, UNION, NULLSET },
      /* A_DIFF_B */ { SET_A, NULLSET, SYMDIFF },
      /* B_DIFF_A */ { SET_B, SYMDIFF, NULLSET },
      /* UNION */ { SYMDIFF, SET_B, SET_A },
      /* SYMDIFF */ { UNION, B_DIFF_A, A_DIFF_B }
  };

  private int currentState;

  public Fsm() {
    this.currentState = NULLSET;
  }

  public void transition(int input) {
    currentState = STATE_TABLE[currentState][input];
  }

  public State getState() {
    return State.values()[currentState];
  }
}

This code is quite simple and compact. A few things to call out:

  1. We dropped the enums and instead use constant static integers. This avoids the call to enum's ordinal() method.
  2. I still kept the getState() return type the same since it's not in the benchmark's hot path.

Tuning Part 3: Cache me if you can

A resource to definitely familiarize yourself with is Jeff Dean's "latency numbers every programmer should know" (slide 24). Though the exact figures might be slightly different today, the orders of magnitude are still the same. Here is a slimmed down version that shows the relevant numbers for us:

Operation Latency Scaled to Human Time (1ns = 1 sec)
CPU Register ~0.3 ns 0.3 seconds
L1 Cache ~0.5 ns 0.5 seconds
L2 Cache ~7 ns 7 seconds
Main Memory (RAM) ~100 ns 100 seconds (1.5 mins)
Solid State Drive (SSD) ~150,000 ns (150 μs) 1.7 days

As you can see, everytime you have to go to the next ladder of the memory hierarchy you are incurring a huge cost. For performance, you want you program to be "cache-friendly", which means that it rarely needs to reach beyond L1 cache (or even registers!) for performance critical code.

The final refactor we'll do will take advantage of how fast register and L1 cache access are.

Now for our 2D table approach, we're actually doing a good job at reducing L1 cache misses but that's actually coincidental. Unlike C and C++ where if you have a 2D array the memory is laid out contiguosly, in Java a list of lists is actually a list of pointers to contiguous blocks on the heap.

C/C++ 2D Array Memory Layout


+-------+-------+-------+-------+-------+-------+
| [0,0] | [0,1] | [0,2] | [1,0] | [1,1] | [1,2] |
+-------+-------+-------+-------+-------+-------+
<----------------- Contiguous Memory ----------->

Java 2D Array Memory Layout (Array of Arrays)


Outer Array (Heap)
+---------+---------+
| Index 0 | Index 1 |
+----|----+----|----+
     |         |
     |         +---------------------------+
     |                                     |
     v                                     v
Inner Array 0 (Heap)                   Inner Array 1 (Heap)
+-------+-------+-------+              +-------+-------+-------+
| [0,0] | [0,1] | [0,2] |              | [1,0] | [1,1] | [1,2] |
+-------+-------+-------+              +-------+-------+-------+

We're not heavily penalized by this misdirection that much (at least in terms of L1 cache misses) here because the first time we fetch the outer array and then the inner arrays and bring them to L1 cache, they are small enough to easily fit. If you have a list of lists that is larger than our example then this might not be the case.

Where this misdirection does hurt us is having to move back and forth due to the pointers. Everytime we have a new state transition, we need to chase the pointer from the outer array to one of the inner arrays and then get the value we need. This results in having to fetch the value stored in L1 cache that is behind the pointer.

To avoid this need for pointer chasing without porting to a language like C++ we can flatten the 2D table to a 1D table like this: 


        +-------+
  [ 0 ] | [0,0] |
        +-------+
  [ 1 ] | [0,1] |
        +-------+
  [ 2 ] | [0,2] |
        +-------+
  [ 3 ] | [1,0] |
        +-------+
  [ 4 ] | [1,1] |
        +-------+
            .
            .
            .
        +-------+
  [23 ] | [7,2] |
        +-------+

For our state machine, now when we have a new input we simply use the formula (currentState * 3) + input. Here is the code: 


// Same use of constants over enums as before
public final class FsmConstants { ... }

public class Fsm {
  private static final int NUM_INPUTS = 3;

  private static final int[] STATE_TABLE = {
      /* NULLSET */ INTERSECT, SET_A, SET_B,
      /* INTERSECT */ NULLSET, SET_A, SET_B,
      /* SET_A */ A_DIFF_B, NULLSET, UNION,
      /* SET_B */ B_DIFF_A, UNION, NULLSET,
      /* A_DIFF_B */ SET_A, NULLSET, SYMDIFF,
      /* B_DIFF_A */ SET_B, SYMDIFF, NULLSET,
      /* UNION */ SYMDIFF, SET_B, SET_A,
      /* SYMDIFF */ UNION, B_DIFF_A, A_DIFF_B
  };

  private int currentState;

  public Fsm() {
    this.currentState = NULLSET;
  }

  public void transition(int input) {
    currentState = STATE_TABLE[(currentState * NUM_INPUTS) + input];
  }

  public State getState() {
    return State.values()[currentState];
  }
}

Wrapping up

By understanding what values help or hurt througput, you can intentionally refactor your code to improve those numbers. For us, we understood that focusing on three major costs (memory allocation, branch misses, and L1 cache misses), we could dramatically improve the performance of our code. This type of machine empathy and the ability to squeeze out as much as you can of the machine is incredibly powerful and can save your business (and the environment!) a great deal over the long run.
