Faster State Machines in JavaScript

2026-07-16

As part of another post I have planned, I wanted to display an interactive Venn diagram to give a brief overview of the basic set operations. When designing this widget, I immediately saw it as a simple state machine. Click one part of the widget and now it's in a new set, etc.

Naively, after scratching out the design with pen and paper I started to implement the machine in JavaScript. Initially I started with the classic "Switch-Case" design. This is likely what everyone first learned with state machine implementations. It's not a bad design since it has a very low memory footprint. The drawback is that the number of switch statements quickly explodes given more states and inputs the machine accepts.

For some reason, even though I generally don't reach for this implementation in lower-level languages, I didn't bring the same rigor to this situation.

For the most part I generally will reach for a state table or something similar that is considered more data-oriented. Althout I'll admit that if I hear something is more "data-oriented" then I am biased towards that approach (thanks Mike Acton), this is something that I've benchmarked in other contexts.

For some reason this problem just stuck in my head. I was sure that a state table implementation should be faster, I really couldn't say why. I've hardly ever done much actual investigation into the innards of V8.

So, even though I'm incredibly busy and had no free time to look into this, I still did. I've shared the code to GitHub so you can see reproduce the benchmarks but below I go into detail about what I found and the learnings I was able to take away.
